# ADR-0004：全项目统一 AGPL-3.0 与三仓合并为单仓

- 状态：已接受（2026-10-09）
- 范围：整个项目（原 `ark-autoplay-core` / `ark-autoplay-maa-bridge` / `ark-autoplay-client`）
- **取代 ADR-0001**（三仓库划分与许可证隔离）
- 合并前各仓 SHA（可随时找回）：
  - core `05a7387dcd7132bf4a49c53220aea6fef8071793`
  - bridge `ec9bcb724abeab84aa2bf6896214c7c09a5799ab`
  - client `35d0611e81409abc16fc558ddf4554d7db241dee`

## 背景

ADR-0001 决定拆分三个独立仓库，理由是**许可证隔离**：MAA/MaaCore 为 AGPL-3.0，若自有代码与其衍生代码同仓或代码级链接，会被传染为 AGPL；而当时的目标是"core / client 保持 Apache-2.0 宽松许可，**可自由商用 / 二次开发**"。

2026-10-09 项目方明确许可意图：

> **项目为纯开源；不允许任何人将本项目代码做成闭源商用项目。**

这直接推翻了 ADR-0001 的前提。同时澄清了另外两个事实：

1. **bridge 当前并非 MAA 衍生作品**：`maacore/`、`patches/` 均为空，运行期仅经 `Asst.load()` 动态加载官方发行版并调用公开 `asst` 接口，不复制、不修改上游源码。故"被传染"这件事**尚未发生**——原 Apache 许可本身也合法。
2. **AGPL-3.0 是 OSI/FSF 认证的开源许可证**：选择 AGPL 与"完全开源"的定位**不冲突**，它恰恰是"开源但禁止闭源商用"的唯一标准做法（非商业条款如 CC-BY-NC 会导致项目**不再是**开源项目）。

## 决策

### 1. 全项目统一 AGPL-3.0

根目录与 `core/`、`bridge/`、`client/` 四处 `LICENSE` 均为同一份 AGPL-3.0 文本（SHA256 一致）；三处 `pyproject.toml` 的 `license` 字段统一为 `AGPL-3.0-only`。

**精确表述**：这是项目方的**主动选择**，不是"被 MAA 传染"的结果——因为当前不含上游源码，调用公开 API 不触发 AGPL 的传染。二者的区别在于：主动选择随时可重新评估；被传染则无选择。

### 2. 三仓合并为单仓 `ark-autoplay`，子目录 `core/` `bridge/` `client/`

采用 `git subtree` 合并，**各仓完整 git 历史全部保留**（上游提交哈希可追溯）。合并后共 17 个提交，三仓原有提交链完整可见。

### 3. 撤销许可证隔离机制

| 撤销项 | 说明 |
|---|---|
| `license-guard` CI 工作流 | 已删除（`core/.github/workflows/license-guard.yml`） |
| "禁止 import bridge/maa" 铁律 | 作废；三个子目录现可自由互相 import |
| "bridge 代码绝不被 core/client import" | 作废 |
| README / AGENTS.md 的隔离表述 | 已改写为"历史沿革"说明 |

**保留**：跨进程边界的**版本化 JSON 协议**。理由不再是许可证，而是它独立成立的工程价值——解耦核心逻辑与设备/模拟器交互，使 `core/` 的单测纯逻辑化（48 个测试 0.5 秒跑完，CI 无需安装 MAA 或模拟器）。

### 4. 更正 bridge 的衍生关系定性

`bridge/NOTICE.md` 原称"本仓库是 MAA 的衍生作品"，与其实际内容（零上游源码）不符，属**过度自认**——法律上主动认领了本不必承担的义务。已改写为双状态声明：当前非衍生；导入 `maacore/` 源码后即为衍生，届时须粘贴上游附加条款原文。

## 后果

- **正**：
  - 许可意图与技术实现一致（禁止闭源商用）；
  - 仓库数 3 → 1，跨目录改动无需跨仓 PR / 协议版本协商；
  - 协议层、`license-guard` CI、依赖方向检查成为**可选项而非强制**，复杂度下降；
  - 消除了"MAA 附加条款未核实"对整体设计的悬空风险——不导入上游源码则不受其约束；
  - 为未来可能的状态导出改造（导入 MaaCore）扫清了法律障碍：全项目同为 AGPL，衍生关系合法且无需变更许可。
- **负**：
  - 失去"core/client 宽松许可便于商用集成"这一选项（**这正是本次决策的目的**）；
  - 单仓体积与 CI 范围变大，需按目录切分测试（`core/tests`、`bridge/tests`、`client/tests` 各自独立）；
  - AGPL 的"网络服务"条款会阻止他人将本项目做成闭源 SaaS。
- **不可逆点**：**已按 Apache-2.0 发布的旧版本，他人仍可依 Apache 条款使用**——改许可只能约束后续版本。故本次变更宜尽早推送。

## 遗留待办

1. **GitHub 侧尚未执行**：本地合并已完成，但新建 `ark-autoplay` 远程仓库、推送、以及三个旧仓的归档/说明，均**未做**（属对外动作，待项目方裁决）。
2. 设计文档《明日方舟AI自主作战-开源项目方案.md》§3（开源策略与许可证）与 §5（项目构成）仍描述三仓方案，需同步修订。
3. 上游 MAA 附加条款原文仍未核实（§17 待核实 #5）；**仅在导入 MaaCore 源码之前**成为必做项。
